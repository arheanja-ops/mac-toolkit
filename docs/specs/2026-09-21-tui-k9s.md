# TUI estilo k9s (Fase TUI-1) — Design Spec

**Date:** 2026-09-21
**Status:** Draft
**Scope:** mac-toolkit CLI (nuevo paquete `internal/tui/`)

## Problem

Hoy la interacción interactiva es `cmd/menu.go`: un `promptui.Select` lineal. El
usuario elige una acción, se ejecuta, imprime a `stderr`, y vuelve al menú. Esto
tiene tres límites:

1. **Sin contexto persistente.** El resultado se pierde al volver al menú; no hay
   scroll ni comparación entre acciones.
2. **Un solo panel.** No se ve a la vez la lista de acciones y su salida.
3. **Navegación pobre.** `promptui` solo hace prompts lineales — no soporta foco
   entre paneles, filtrado en vivo, ni layout con header/footer vivos.

Se necesita una TUI de pantalla completa estilo k9s: dos paneles, navegación por
teclado, header con contexto vivo y footer de atajos. Debe **reutilizar** los
analyzers y monitores existentes, no reimplementar lógica.

## Features

### F1: `mac-toolkit tui` — shell de la TUI

**CLI:** `mac-toolkit` (sin args, nuevo default) · `mac-toolkit tui` (explícito)
**Fallback:** `mac-toolkit menu` conserva el menú `promptui` actual intacto.

Behavior:
1. `mac-toolkit` sin subcomando abre la TUI (antes abría `runMenu`). El `Run` del
   `rootCmd` pasa a invocar `tui.Run()`.
2. `mac-toolkit tui` es el alias explícito del mismo comportamiento.
3. `mac-toolkit menu` queda registrado como subcomando que llama a `runMenu()`
   (el `promptui` de hoy) — fallback para terminales sin soporte o preferencia.
4. Todos los comandos directos (`analyze`, `system`, `battery`, `network`,
   `processes`, `status`, `clean`, `docker`, `report`, `full`, `mcp`) siguen
   idénticos. La TUI es aditiva.

Constraints:
- No reemplaza `cmd/menu.go` ni ningún comando. Solo cambia el `Run` del root
  para que el default sea la TUI en vez del menú.
- El servidor MCP (`mac-toolkit mcp`) no se toca.
- Si la TUI no puede inicializar (p. ej. no hay TTY), degrada con un error claro
  sugiriendo `mac-toolkit menu` o un subcomando directo.

### F2: Layout de 2 paneles

```
┌─ mac-toolkit v1.x.x  Disk ▓▓▓▓▓░░ 62% 128G free · Mem 71% · CPU 34% · 🌡 OK ─┐
│ DISK              │  Analyze — full disk scan                                  │
│  ▸ Analyze        │  ────────────────────────────────────────────────         │
│    Status         │  dev_caches   12.4 GB   safe    npm/pip/brew               │
│ MONITORS          │  browser       3.1 GB   safe    Chrome/Safari cache        │
│    Battery        │  xcode        18.7 GB   warn    DerivedData/Simulators     │
│    System         │  ...                                    (scroll ↑↓)        │
│    Processes      │                                                            │
│    Network        │                                                            │
│ REPORTS           │                                                            │
│    Last report    │                                                            │
└───────────────────┴────────────────────────────────────────────────────────────┘
 ↑↓ nav · Tab foco · ⏎ ejecutar · / filtrar · q salir
```

Behavior:
1. **Panel izquierdo (acciones):** lista agrupada `Disk / Monitors / Reports` con
   los mismos headers y entradas que `menuOptions`, menos las acciones
   destructivas (ver F5). Headers no seleccionables.
2. **Panel derecho (detalle):** viewport con scroll que muestra la salida de la
   acción ejecutada. Vacío al inicio con un hint ("⏎ para ejecutar").
3. **Header vivo (ver F6):** contexto del PC actualizándose **en vivo, siempre** —
   `version` + disco (uso %, libre) + memoria (%) + CPU (%) + estado térmico. No
   depende de que el usuario ejecute una acción: se refresca solo mediante un tick
   periódico.
4. **Footer:** línea fija de atajos.

Constraints:
- El header reutiliza `core.ReadDiskSnapshot()` y los monitores `system` para
  memoria/CPU/thermal; cualquier lectura que falle se omite sin romper el header
  (degrada campo a campo, muestra al menos `version`).
- El layout es responsive al tamaño de terminal (Lipgloss calcula anchos); ancho
  mínimo razonable ~80 cols, si es menor colapsa el panel izquierdo a labels
  cortos y el header a solo disco + memoria.

### F3: Navegación estilo k9s

Behavior:
| Tecla        | Acción                                                        |
|--------------|---------------------------------------------------------------|
| `↑` / `↓`    | Mover selección en el panel con foco                          |
| `Tab`        | Alternar foco entre panel izquierdo (acciones) y derecho (detalle) |
| `Enter`      | Ejecutar la acción seleccionada; renderiza en panel derecho   |
| `/`          | Filtrar la lista de acciones (fuzzy sobre el label)           |
| `Esc`        | Salir del modo filtro; si no hay filtro, salir de la TUI      |
| `q`          | Salir de la TUI                                               |
| `PgUp/PgDn`  | Scroll del viewport de detalle cuando tiene foco              |

Constraints:
- El foco se indica visualmente (borde resaltado del panel activo, patrón k9s).
- El filtro `/` solo aplica al panel de acciones; nunca borra ni ejecuta.
- Salida siempre disponible con `q`; `Esc` es contextual (filtro → TUI → salir).

### F4: Ejecución de acciones (solo lectura, reutiliza lógica)

Behavior:
1. Al pulsar `Enter`, la TUI ejecuta la lógica del analyzer o monitor
   correspondiente y **captura su salida** para renderizarla en el viewport.
2. **Analyze:** invoca la ruta de análisis existente (`core.RunAnalyzers` sobre
   los `analyzer.Analyzer` registrados) y formatea los `core.AnalysisResult`
   (dominio, tamaño, riesgo, resumen) en el panel derecho.
3. **Monitores:** cada uno de los 4 monitores implementa la interfaz
   `monitor.Monitor` (`Name()`, `Snapshot()`, `Display()`). La TUI usa
   `Snapshot()` para obtener `map[string]any` y lo formatea, o captura la salida
   de `Display()`. No reimplementa `ioreg`/`pmset`/`system_profiler`/etc.
4. **Status:** reutiliza la lógica de `statusCmd` (dominios registrados + niveles
   de riesgo).
5. La ejecución corre en un `tea.Cmd` (goroutine) para no bloquear el event loop;
   mientras corre, el panel derecho muestra un spinner (Bubbles).

Constraints:
- **Solo lectura.** Fase TUI-1 no expone ninguna acción que borre o modifique:
  ni `clean`, ni `docker cleanup/backup/compact`, ni `full`.
- Reutiliza los analyzers y monitores tal cual — la TUI es una capa de
  presentación, no una nueva fuente de verdad.
- Errores de una acción se muestran en el panel derecho, nunca tumban la TUI.

### F5: Acciones incluidas en Fase TUI-1

Panel izquierdo (subconjunto de solo lectura de `menuOptions`):

| Grupo    | Acción      | Origen reutilizado                         |
|----------|-------------|--------------------------------------------|
| Disk     | Analyze     | `core.RunAnalyzers` + analyzers registrados |
| Disk     | Status      | lógica de `statusCmd`                       |
| Monitors | Battery     | `monitor.Monitor` (battery)                 |
| Monitors | System      | `monitor.Monitor` (system)                  |
| Monitors | Processes   | `monitor.Monitor` (processes)               |
| Monitors | Network     | `monitor.Monitor` (network)                 |
| Reports  | Last report | lógica de `reportCmd` (`--last`)            |

Constraints:
- `Preview`, `Clean` y `Full flow` (presentes en `menuOptions`) se **omiten** en
  Fase TUI-1 por ser escritura o dry-run interactivo (ver Non-goals).

### F6: Header vivo (refresco continuo del estado del PC)

El header muestra el estado del PC **en tiempo real y siempre**, independiente de
la navegación o de ejecutar acciones.

Behavior:
1. Al iniciar, la TUI programa un tick periódico con `tea.Tick` (intervalo
   configurable, default **2s**). Cada tick dispara un `tea.Cmd` que lee las
   métricas ligeras y devuelve un `headerTickMsg`.
2. Métricas del header (todas de bajo costo):
   - **Disco:** `core.ReadDiskSnapshot()` → barra + % + libre.
   - **Memoria:** % usado, vía el monitor `system` (`Snapshot()`), campo memoria.
   - **CPU:** % de uso, del mismo monitor `system`.
   - **Térmico:** estado (`OK` / `Warning` / …) del monitor `system`.
3. La lectura de métricas corre en un `tea.Cmd` (goroutine) para no bloquear el
   event loop; el `Update` solo aplica el resultado del `headerTickMsg` y
   reprograma el siguiente tick.
4. El refresco del header es **independiente** de la ejecución de acciones del
   panel derecho: aunque el usuario no haga nada, el header sigue vivo.

Constraints:
- Intervalo por defecto 2s; evitar comandos costosos (`system_profiler` completo)
  en el path del tick — usar solo las lecturas ligeras que ya exponen los
  monitores. Si una métrica no está disponible en un tick, se conserva el último
  valor válido o se omite ese campo.
- El tick se detiene al salir de la TUI (no deja goroutines colgadas).
- Degradación: si `system` falla, el header mantiene disco (que casi nunca falla)
  y omite mem/CPU/thermal sin romper el layout.
- El costo del refresco debe ser despreciable; si en la práctica el monitor
  `system` resulta pesado, el intervalo se sube o se cachea — pero eso es
  detalle de implementación, no cambia el contrato de "header vivo".

## Dependencias

Se añaden **3 dependencias nuevas** (charmbracelet):

| Dep                          | Rol                                         |
|------------------------------|---------------------------------------------|
| `github.com/charmbracelet/bubbletea` | Event loop / modelo Elm (Init/Update/View) |
| `github.com/charmbracelet/lipgloss`  | Layout, bordes, colores de paneles         |
| `github.com/charmbracelet/bubbles`   | Componentes: `list`, `viewport`, `spinner` |

Justificación: `promptui` (dep actual) solo hace prompts lineales — no soporta
pantalla completa, foco entre paneles, viewport con scroll ni header/footer
vivos. Una TUI k9s-like requiere un runtime de UI declarativa; Bubble Tea es el
estándar de facto en Go y el trío es cohesivo. La regla "zero runtime deps más
allá de cobra" se relaja **deliberadamente y solo para el paquete `internal/tui/`**;
los comandos directos y el MCP siguen sin depender de charmbracelet. `promptui`
se mantiene (lo usa `cmd/menu.go`, que no se elimina).

## Data model

La TUI no introduce structs de dominio nuevos: consume los existentes.

```
// Estado del modelo Bubble Tea (interno a internal/tui/)
model {
  focus      Panel          // ActionsPanel | DetailPanel
  actions    list.Model     // Bubbles list con los items de F5 (grupos + acciones)
  detail     viewport.Model // salida scrolleable de la última acción
  spinner    spinner.Model  // visible mientras corre un tea.Cmd
  disk       core.DiskSnapshot // header vivo (core.ReadDiskSnapshot)
  hdr        headerStats    // métricas vivas del header (F6)
  filtering  bool           // modo '/'
  err        error          // último error de acción, si lo hubo
}

// headerStats: métricas ligeras refrescadas por tick (F6).
headerStats {
  memUsedPct  int
  cpuUsedPct  int
  thermal     string   // "OK" | "Warning" | ...
  ok          bool     // false si la última lectura de system falló
}

actionItem {
  label   string
  group   string            // "Disk" | "Monitors" | "Reports"
  run     func() (string, error) // adapta analyzer/monitor a texto renderable
}
```

Reutilizados sin cambios: `core.DiskSnapshot`, `core.AnalysisResult`,
`analyzer.Analyzer`, `monitor.Monitor`.

## Non-goals (Fase TUI-1)

- **Clean interactivo** (preview + aprobación + borrado dentro de la TUI) →
  Fase **TUI-2**.
- **Panel Doctor de IA** (diagnóstico priorizado dentro de la TUI) → Fase
  **TUI-3**, depende de [AI Doctor](2026-09-09-ai-doctor.md).
- Polling/refresh automático del **panel de detalle** (re-ejecutar analyze/monitor
  en background y actualizar el viewport solo) → futuro. Nota: el **header** sí se
  refresca en vivo (F6); lo que queda fuera es auto-refrescar el detalle.
- Reemplazar `cmd/menu.go` o los comandos directos → nunca; la TUI es aditiva.
- Mouse support, temas configurables, exportar la vista → fuera de alcance F1.

## Testing

- **Adaptadores de acción:** tests de las funciones `run()` que envuelven
  analyzers/monitores → devuelven `(string, error)` con inputs mockeables (o
  sobre snapshots fijos donde aplique), sin depender del hardware real.
- **Modelo `Update`:** tests de transiciones de estado con mensajes sintéticos de
  Bubble Tea (`tea.KeyMsg` para `Tab`, `/`, `Enter`, `q`) verificando cambios de
  `focus`, `filtering` y disparo de `tea.Cmd`.
- **Header:** test de que con `DiskSnapshot{OK:false}` el header no rompe y omite
  la barra.
- **Header vivo (F6):** test de que `headerTickMsg` actualiza `headerStats` y
  reprograma el tick; y de que con `headerStats{ok:false}` el header conserva el
  disco y omite mem/CPU/thermal sin romper el layout.
- **No-regresión:** `mac-toolkit menu` sigue ejecutando el `promptui` actual;
  comandos directos y MCP intactos. `go build ./...` y `go vet ./...` limpios.
- Nota: el render pixel-a-pixel de la TUI no se testea; se prueban la lógica de
  estado y los adaptadores, no `View()`.
