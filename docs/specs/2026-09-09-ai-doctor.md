# AI Doctor (Fase 1) — Design Spec

**Date:** 2026-09-09
**Status:** Draft
**Scope:** mac-toolkit CLI + MCP server
**Roadmap:** [AI & Agents Roadmap](2026-09-09-ai-roadmap.md) — Fase 1

## Problem

El toolkit muestra datos crudos pero no los interpreta. El usuario ve tablas
(`appsupport 36 GB`, `swap 21 GB`, `thermal Warning`) y tiene que deducir él mismo
qué es urgente, qué es basura segura y qué es dato del sistema. Peor: el resumen
actual suma el dominio `disk` (uso total del volumen, ~346 GB) con la basura
limpiable, produciendo un "Total" engañoso.

Se necesita una capa que traduzca métricas en un **plan priorizado accionable**,
usando IA cuando esté disponible y heurísticas deterministas cuando no.

## Features

### F1: `toolkit doctor`

**CLI:** `toolkit doctor` · `toolkit doctor --no-ai` · `toolkit doctor --json`
**MCP:** `mac_doctor {}` (reutiliza el snapshot; devuelve el diagnóstico estructurado)

Behavior:
1. Ejecuta todos los analyzers + monitores (reusa `runAnalysis` y los monitores
   existentes) y arma un `Snapshot`.
2. Construye un **snapshot agregado** para IA (ver F3): tamaños por dominio,
   severidad, conteo de items, métricas de sistema — **sin rutas ni nombres de
   archivo**.
3. Si hay `GROQ_API_KEY` y no está `--no-ai`: envía el snapshot a Groq (F2) y
   recibe un `Diagnosis` estructurado.
4. Si no hay key, o falla la llamada, o está `--no-ai`: usa el motor heurístico
   (F4). El resultado tiene el mismo shape.
5. Renderiza el diagnóstico (F5) o lo emite como JSON con `--json`.

Constraints:
- Solo lectura. `doctor` nunca borra ni ejecuta acciones.
- La distinción "estado del sistema" vs "basura limpiable" es obligatoria: el
  dominio `disk` se reporta como contexto, nunca se suma al total recuperable.
- Nunca falla por ausencia de IA: sin key → heurístico, sin ruido de error.

### F2: Cliente Groq — `internal/ai`

OpenAI-compatible chat completions vía `net/http` stdlib (sin SDK externo).

Behavior:
1. `POST {GROQ_BASE_URL}/chat/completions` con `Authorization: Bearer $GROQ_API_KEY`.
2. `response_format: { type: "json_object" }` para forzar salida estructurada.
3. System prompt: experto en optimización macOS; prioriza por impacto; distingue
   basura de datos del sistema; nunca recomienda borrar items de riesgo `danger`;
   responde SOLO el JSON del schema `Diagnosis`.
4. User message: el snapshot agregado (F3) serializado.
5. Timeout configurable (default 20s). Un fallo → error recuperable → fallback F4.

Constraints:
- `GROQ_API_KEY` solo desde entorno. Nunca en logs, nunca en el repo, nunca en
  audit. Si aparece en un error de la librería HTTP, se redacta antes de loguear.
- Valida y parsea el JSON de respuesta contra el schema; si no matchea → fallback.
- Modelo y endpoint configurables por env (ver roadmap). Default
  `openai/gpt-oss-20b`.

### F3: Snapshot agregado (privacidad)

Struct enviado a la IA — **agregados, sin PII**:

```
AISnapshot {
  disk_used_pct, disk_free_bytes, disk_total_bytes   // contexto, no "limpiable"
  domains: [ { domain, severity, size_bytes, item_count, top_risk } ]  // sin paths
  reclaimable_safe_bytes, reclaimable_total_bytes     // ya excluye `disk`
  memory_used_pct, swap_used_bytes
  cpu_usage_pct, thermal_state
  top_cpu_process { name, cpu_pct }                    // solo el #1, sin PID
}
```

Constraints:
- Prohibido incluir rutas absolutas, nombres de archivo, nombres de repos, PIDs.
- La anonimización ocurre al construir el snapshot, no confía en el prompt.

### F4: Motor heurístico determinista — `internal/ai` (fallback)

Reglas fijas que producen el mismo `Diagnosis` sin llamar a la IA:

| Regla | Condición | Insight |
|-------|-----------|---------|
| Memoria | `swap_used > 10GB` o `mem_used_pct > 85` | performance/alta: presión de memoria |
| Térmico | `thermal != nominal` y `top_cpu_pct > 40` | performance: proceso caliente |
| Disco | `disk_used_pct >= 85` | disco crítico | `70-85` recomendado | `<70` opcional |
| Quick win | dominios con `top_risk == safe` | suma como recuperable seguro |
| Revisión | dominios con `warn`/`danger` | listar sin auto-acción |

Constraints:
- Determinista y testeable con inputs fijos.
- Es la fuente de verdad del schema `Diagnosis`; la IA se ajusta a él, no al revés.

### F5: Renderizado

Salida agrupada por prioridad, reusando helpers de `core` (colores, `ProgressBar`,
`FormatBytes`):

```
🩺 Diagnóstico  (motor: groq · openai/gpt-oss-20b | heurístico)

  ⚡ PERFORMANCE
     • <insight> — <acción sugerida>
  🧹 QUICK WINS  (X GB recuperables sin riesgo)
     • <dominio> <tamaño> — <por qué es seguro>
  ⚠ REQUIERE REVISIÓN  (Y GB)
     • <dominio> <tamaño> — <por qué revisar>

  Contexto: disco al Z% (N GB libres de M GB)
```

Constraints:
- Indica siempre qué motor produjo el diagnóstico (transparencia IA vs heurístico).
- `--json` emite el `Diagnosis` sin colores para scripting/MCP.

## Data model

```
Diagnosis {
  engine: "groq" | "heuristic"
  performance: [ Insight ]     // { title, detail, action, severity }
  quick_wins:  [ Insight ]     // acciones seguras, con bytes recuperables
  review:      [ Insight ]     // requiere decisión del usuario
  reclaimable_safe_bytes: int64
  context: { disk_used_pct, disk_free_bytes, disk_total_bytes }
}
```

## Non-goals (Fase 1)

- Function-calling / agente conversacional → Fase 2.
- Ejecutar limpieza u optimización desde `doctor` → Fase 3.
- Monitoreo recurrente en background → Fase 4.
- Proveedores distintos de Groq (el cliente queda genérico OpenAI-compatible, pero
  solo se prueba Groq).

## Testing

- `internal/ai` heurístico: tabla de inputs (snapshots) → outputs esperados.
- Cliente Groq: test con servidor HTTP mock (`httptest`) validando request
  (headers, body, redacción de key en errores) y parseo de respuesta.
- Redacción de secreto: test que confirma que la key nunca aparece en salida/logs.
- Privacidad: test que confirma que `AISnapshot` no contiene paths ni PIDs.
